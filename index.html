01 / ABOUT ME

좋아하는 경험을
실제 플레이로 옮깁니다.

저는 좋아했던 게임 경험을 분석해 제 방식으로 다시 구현하는 게임 클라이언트 프로그래머입니다. 게임을 즐길 때면 “무엇이 이 장면을 재미있게 만드는가?”, “이 경험을 플레이 규칙으로 옮기려면 어떤 구조가 필요한가?”를 생각합니다. 떠오른 아이디어는 직접 만들어 확인합니다.

첫 팀 프로젝트로 제작한 마인크래프트 던전에서는 좋아하던 쿠크세이튼 레이드 기믹을 바탕으로 최종 보스의 2개 페이즈를 구현했습니다. 여기에 반려묘 보리·루이·호떡을 보스 패턴에 담고 고양이 리소스와 애니메이션도 직접 만들었습니다. 좋아했던 경험과 개인적인 소재를 실제 전투로 완성한 작업이었습니다.

게임 개발을 직업으로 선택한 계기는 출장이 잦던 시기에 친구들과 시작한 로스트아크였습니다. 출장 때문에 함께 보드게임을 즐기기 어려워졌지만 게임 안에서는 같은 목표에 몰입하고 이야기를 쌓을 수 있었습니다. 그때 게임이 사람을 연결하는 힘을 처음 실감했습니다. NDC21의 ‘처음 만드는 건데 실수 좀 할 수 있죠’를 접한 뒤에는 실패를 감추기보다 원인을 돌아보고 다음 시도에 반영하는 개발 태도에 끌렸습니다. 기본기와 엔진 원리를 배우기 위해 C++·DirectX 과정을 선택한 것도 그때였습니다.

무대 시공 현장관리와 3D 기구설계에서 요구사항을 구조로 옮기던 경험은 지금의 개발 방식으로 이어졌습니다. 현재는 C++와 Unreal Engine으로 전투와 상호작용을 구현하며 좋아했던 경험을 다른 사람도 즐길 수 있는 플레이로 만드는 일을 계속하고 있습니다.

6인 DirectX 11 팀 프로젝트에서 주간 목표를 채우지 못한 적이 있습니다. 각자 작업을 진행하고 있었지만 서로 어디에서 막혔는지는 잘 알지 못했습니다. 저는 하루 작업을 마치기 전 화이트보드에 진행 상황과 어려움을 적고, 다음 날 아침 함께 확인하자고 제안했습니다. 모두가 모인 자리에서 취지를 설명하고 시도해 보자고 설득했습니다.

저부터 이펙트 툴 연동 중 막힌 부분을 적어 도움을 요청했습니다. 팀원들도 어려움을 기록했고, 아침마다 팀장과 관련 개발자들이 해결 방법을 함께 논의했습니다. 지금도 팀원들을 만나면 제 제안 덕분에 목표치를 채울 수 있었고, 그때만큼 몰입한 적이 없었다는 이야기를 듣습니다.

돌이켜보면 실패와 막힘까지 나눈 저희 팀만의 작은 NDC였습니다. 시행착오를 숨기지 않고 공유할 때 팀이 앞으로 나아갈 수 있다는 것을 배웠습니다. 함께 고민하며 목표를 채워 나갔던 이 프로젝트는 제게도 빛나는 경험으로 남아 있습니다.

03 / PROBLEM-SOLVING ABILITY

막힌 문제는 더 작은 동작으로
나눠 해결합니다.

구현 방법이 바로 떠오르지 않으면 동작을 작은 단위로 나누고 실제 값을 확인하며 답을 찾습니다.

6인 DirectX 11 팀 프로젝트에서는 다른 팀원이 만든 기능을 분석해 제 작업과 연결하는 일이 익숙하지 않았습니다. 플레이어가 염력으로 던진 물체를 최종 보스가 붙잡아 다시 되던지는 패턴을 맡았습니다. 짧은 시간 안에 물체와 보스의 동작이 빠르게 이어져 구현하기 어려웠습니다.

계속 코드를 읽는 것만으로는 답이 나오지 않았습니다. 추측만으로 해결할 수 없다면 이 동작을 쪼개고 더 쪼개 보자고 생각했습니다.

먼저 패턴을 물체의 움직임을 멈추고, 보스 앞으로 가져오고, 공격 동작에 맞춰 플레이어에게 되돌려 보내는 세 단계로 나눴습니다. 각 단계는 물체의 상태가 바뀌는 지점을 기준으로 다시 나눴습니다. 중단점과 조사식으로 값과 애니메이션 재생 시간도 확인했습니다. 이를 바탕으로 물체의 움직임을 멈춘 뒤 보스의 동작에 맞춰 다시 움직이면 된다는 가설을 세웠고 실제 동작을 확인하며 하나씩 연결했습니다.

해당 패턴을 일정 안에 완성해 최종 보스의 8개 패턴 중 하나로 적용했습니다. 처음에는 경험이 부족했지만 문제를 작은 단계로 나누면 끝까지 구현할 수 있다는 자신감을 얻었습니다. 지금도 구현이 막히면 동작을 더 작게 나누고 추측에 기대기보다 중단점과 조사식으로 실제 값과 동작을 직접 확인합니다. 맡은 기능을 일정 안에 마무리하기 위해 단련한 제 코딩 습관입니다.

오래 즐겨 온 수영은 개발 기간 동안 체력과 집중력을 유지하는 데 큰 도움이 됐습니다. 일정이 바쁠 때도 주말마다 수영을 이어가며 꾸준히 개발에 집중했습니다.

먼저 동작하는 형태를 만든 뒤에는 한 가지 방식에 머물지 않습니다. 예상한 흐름과 다르게 움직이거나 이후의 기능을 받아들이기 어려운 구조라면 다른 관점에서 다시 살펴보고 필요한 부분을 리팩터링합니다. 이미 들인 시간이 아깝다고 기존 논리를 붙잡지 않습니다. 불필요한 부분은 덜어내고 다른 방법을 시도합니다.

여러 조건이 맞물려 기능이 제대로 움직이고 처음 만든 코드가 다음 변화까지 받아들일 수 있는 구조로 다듬어지면 퍼즐을 맞춘 듯한 짜릿함을 느낍니다. 그 즐거움은 더 나은 방법을 계속 찾게 하는 제 발전의 원동력입니다.

저에게 완성도는 처음부터 모든 것을 완벽하게 만드는 데서 나오지 않습니다. 지금 필요한 기능을 먼저 움직이고 확인한 결과를 바탕으로 한 단계씩 다듬는 데서 만들어집니다. 작업이 복잡해질수록 ‘지금 가장 먼저 끝내야 할 것은 무엇인가’를 생각합니다. 그 답에 시간과 집중력, 체력을 모으는 것이 제 자원 관리 방식입니다.

02 / DAMAGE EVENTS

Any Damage의 중복 처리 제한

Point Damage 뒤에 Any Damage도 호출되어 하나의 피격이 공통 처리로 두 번 들어오는 경우를 다뤘습니다.

피격 정보와 처리 경로 통합

Point·Radial·Any Damage 이벤트를 Process Damage로 모았습니다. 피해량, 피격 위치·방향, 공격자 등을 DamageInfo 구조체에 담고, 체력을 갱신한 뒤 Damage Tag에 맞는 행동을 실행합니다.

Any Damage가 이어질 때 검사

Process Damage에서 Get Frame Count 값을 저장합니다. Any Damage를 받을 때 저장된 값과 현재 프레임이 같으면 건너뛰고, 다를 때만 공통 함수를 실행합니다. Point Damage 뒤에 이어지는 Any Damage로 같은 피격을 다시 처리하지 않도록 한 분기입니다.

프레임 번호로 구분하는 범위

Point·Radial Damage는 이 검사 없이 공통 함수로 들어갑니다. Any Damage 경로는 공격자나 공격 ID를 비교하지 않으므로, 같은 프레임에 들어온 별개의 Any Damage까지 구분하는 방식은 아닙니다.

SetStress에서는 게이지를 누적하고 최대치에 도달하면 StartStress를 호출합니다. 게이지가 최대치로 남는 부분과 StartStress에서 이미 스트레스 상태인지 검사하지 않는 부분을 짚었습니다.

최대치에 도달한 게이지

상태가 시작될 때 게이지를 0으로 되돌리도록 초기화 위치를 제안했습니다. 기존 초기화 경로와 비교해 다음 피격에서도 최대치가 그대로 사용되는 부분을 확인했습니다.

상태 중복 진입

StartStress의 진입 조건에 IsStress를 추가하도록 제안했습니다. 게이지 누적 단계의 검사와 별개로, 상태를 시작하는 함수에서도 이미 실행 중인지 확인하도록 했습니다.

01 / WORKFLOW

구현 전에 방향을 맞추고, 판단의 맥락을 남깁니다.

약 1년 동안 개발된 프로젝트에 합류해 기존 전투를 새 기획에 맞게 바꾸고 있습니다. 다른 팀원이 만든 동작을 확인하고 구현 의도에 대한 가설을 세운 뒤, 어떤 부분을 어떻게 바꿀지 먼저 정리합니다.

작업 방향을 먼저 검토받습니다.

작업 요청이 들어오거나 기획안에 따라 구현할 때는 변경할 내용과 작업 방법을 문서로 작성합니다. 이 문서를 검토받은 뒤 작업을 시작합니다. 모두 만든 뒤에야 방향이 다르다는 것을 알게 되면 재작업 비용이 커지기 때문에, 구현 전에 서로 생각한 동작이 맞는지 확인합니다.

작업 노트에 판단 과정을 기록합니다.

Outline에는 요청 명세와 기능별 문서, 작업 노트를 나눠 정리합니다. 작업 노트에는 매일 무엇을 했는지, 어디에서 어려움을 겪는지, 어떤 이유로 그 방법을 택했는지 적습니다. 결과만으로는 전달하기 어려운 판단의 맥락을 남겨 다른 팀원도 작업 중에 확인할 수 있도록 합니다.

  1. 01요청과 기존 동작 확인

    기획안과 현재 구현을 비교합니다.

  2. 02변경안 작성

    바꿀 내용과 작업 방법을 문서로 정리합니다.

  3. 03검토 후 구현

    작업 방향을 확인받고 구현을 시작합니다.

  4. 04작업하며 기록

    진행 상황·어려움·판단 이유를 일자별로 남깁니다.

02 / WEAPON TRANSITION

무기 전환의 요청과 확정 시점을 나눴습니다.

애니메이션 시점에 맞춘 장착 상태 변경

무기 교체 입력과 실제로 장착·수납하는 시점은 다릅니다. 입력을 받으면 바꿀 무기와 요청 상태를 보관하고, 교체 몽타주를 재생하도록 수정했습니다.

  1. 01교체 요청 보관

    전환할 무기를 정하고 요청을 예약합니다.

  2. 02전환 동작 실행

    교체 몽타주와 장착·수납 동작을 시작합니다.

  3. 03Notify에서 확정

    해당 시점에 실제 장착 상태를 바꿉니다.

확정 전에 중단된 경우

Notify 전에 피격으로 동작이 중단되면 예약한 요청을 취소합니다. 아직 바뀌지 않은 장착 상태가 교체된 것으로 남지 않도록 구분했습니다.

이미 변경된 경우

Notify를 지난 뒤에는 확정된 무기 상태를 기준으로 후속 동작을 처리합니다. 입력 여부와 실제 장착 결과를 같은 시점의 값으로 다루지 않도록 정리했습니다.

03 / IMPLEMENTATION

락온과 피격 기능의 연동

락온 탐색·검사·해제

락온을 전담 컴포넌트로 옮기고 공격·처형·UI·카메라의 호출부를 새 컴포넌트에 맞췄습니다. 입력으로 후보를 찾은 뒤 대상의 생존 여부와 거리, 시야 가림을 검사합니다.

대상을 다시 찾는 경우

현재 대상이 사망하거나 유효하지 않으면 다른 후보를 탐색합니다. 새 대상을 찾으면 타깃과 UI·카메라 기준을 갱신하고, 후보가 없으면 락온을 해제합니다.

거리와 시야 조건

허용 거리를 벗어난 대상은 락온을 해제합니다. 거리 안에서 시야가 가려진 경우에는 다른 대상을 탐색하도록 조건을 나눴습니다.

체력·피격·처형 가능 상태 관리

체력 변경과 처형 가능 여부를 피격 반응 컴포넌트에서 관리하도록 모았습니다. 적 UI는 체력이 바뀔 때 Delegate로 알림을 받아 갱신하고, 다른 전투 기능은 이 컴포넌트의 상태를 참조하도록 수정했습니다.

전투 기능 간 연동

타깃 정책·전투 카메라·회피·무기·VFX의 호출을 변경된 전투 흐름에 맞췄습니다.
