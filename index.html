01 / CONTEXT

작업량이 늘어날수록, 이펙트는 개별 오브젝트가 아니라 관리 체계가 필요했습니다.

전투마다 새 이펙트를 붙이는 방식으로는 속도와 일관성을 유지하기 어려웠습니다. 그래서 렌더러의 이펙트 전용 그룹과 타깃을 분리하고, 제작자가 값과 재생 흐름을 조절할 수 있는 VFX 관리 구조를 먼저 설계했습니다.

DESIGN

Manager → Group → System

VFX Manager가 수명주기와 호출을 관리하고, EffectGroup이 여러 EffectSystem을 묶어 전투 한 번의 연출 단위로 다루도록 구성했습니다. 개별 버퍼는 각 이펙트의 표현과 갱신에 집중하도록 역할을 나눴습니다.

OUTCOME

반복 조정의 기준을 통일

호출 위치와 순서가 흩어지지 않도록 관리 지점을 모아, 패턴별 VFX를 같은 흐름 안에서 연결할 수 있게 했습니다.

02 / TOOLING & OPTIMIZATION

이펙트 값은 코드 수정이 아니라,
도구에서 확인하며 다듬었습니다.

ImGui 기반 도구에서 Curve, Burst, 충돌 파티클, 빌보드·데칼·부착 방식을 조정하고 JSON으로 저장·불러오는 흐름을 만들었습니다. 같은 버퍼를 반복 생성하지 않도록 로컬 변환값을 활용해 재사용하는 방식도 적용했습니다.

IMPLEMENTATION NOTES
  1. 01
    실시간 파라미터 조정

    곡선과 재생량을 도구에서 바꿔 보며, 전투에서 필요한 타이밍과 밀도를 빠르게 확인했습니다.

  2. 02
    JSON 기반 프리셋

    조정한 값을 저장·재사용해 이펙트 설정이 장면과 코드에 흩어지지 않도록 정리했습니다.

  3. 03
    버퍼 재사용

    반복 인스턴스는 로컬 변환값으로 차이를 두어, 중복 버퍼 생성과 렌더링 비용을 줄이는 방향으로 구성했습니다.

03 / FINAL BOSS

보스 패턴은 상태와 이벤트를 기준으로,
연출·충돌·판정을 함께 연결했습니다.

카렌의 1·2페이즈와 8개 패턴은 거리와 쿨다운을 판단하는 Controller를 중심으로 구성했습니다. 행동의 시작과 종료는 상태 단위로 분리하고, 애니메이션 이벤트가 발생하는 시점에 이펙트와 충돌 판정이 호출되도록 연결했습니다.

PATTERN FLOW

판단 → 행동 → 피드백

원거리에서는 아이스 니들·전기 구체, 근거리에서는 돌진·카운터처럼 조건에 맞는 패턴을 선택했습니다. 플레이어가 던진 오브젝트를 잡아 되던지는 패턴은 동료의 플레이어 코드를 분석하고 통신하며 연결했습니다.

DAZ에서 준비한 캐릭터를 Blender와 Mixamo를 거쳐 Unreal Engine으로 옮기고, 메시·리그·애니메이션이 프로젝트 안에서 일관되게 동작하도록 정리했습니다. Material과 Control Rig도 전투 연출에 맞춰 조정했습니다.

01 / COLLISION

두 종류의 충돌로 나눠 구현했습니다.

오브젝트 간 접촉에는 AABB를, 경사진 지면을 밟는 처리에는 Line 충돌을 적용했습니다. 충돌 검사는 매니저가 그룹 단위로 수행하고, 각 오브젝트가 자신의 Collision Event를 처리하도록 역할을 분리했습니다.

01 / AABB

사각형 접촉과 반응량

오브젝트의 최소·최대 좌표를 비교해 접촉을 판단하고, X·Y축 충돌량을 남겨 밀어내기와 피격 반응에 사용했습니다. 플레이어와 적·투사체가 같은 방식으로 판정되도록 기반을 마련했습니다.

02 / LINE

지면 위에 서는 처리

플레이어 X좌표 아래의 선분 교점을 계산해 Y 위치를 보정했습니다. LineManager가 지면 검사를 맡아 점프·낙하 상태가 바닥 정보에 의존하도록 연결했습니다.

02 / STATE & RENDERING

행동은 상태로, 화면 표시는 리소스 관리로 정리했습니다.

Idle·Run·Jump·Attack·Dash·Parry·Hit 등 캐릭터 동작을 상태로 나누고, 입력과 충돌 결과가 상태 전환으로 이어지게 구성했습니다. 렌더링에서는 이미지를 메모리 DC에 로드해 키로 관리하고, 투명 블리팅과 디버그 히트박스를 함께 처리했습니다.

STATE MACHINE
  1. 01

    행동에 따라 애니메이션 프레임과 갱신 규칙이 바뀌도록 switch 기반 상태 흐름을 구성했습니다.

  2. 02
    입력과 충돌의 연결

    키 입력, 지면 여부, 피격 판정이 각각 다음 상태를 결정하는 조건이 되도록 연결했습니다.

GDI RENDERING

보이는 것과 판정되는 것을 함께 확인

리소스 매니저에서 BMP를 불러오고, 투명 처리와 디버그 히트박스를 같은 화면에 표시해 렌더링 결과와 충돌 범위를 빠르게 확인했습니다.

03 / PROBLEM SOLVING

처음에는 막막했던 구현을,
문제를 쪼개고 검증하는 방식으로 풀었습니다.

02 / BOSS BEHAVIOR

멀티플레이 보스는 상태·충돌·애니메이션의 시간을 맞추는 작업이었습니다.

보스의 망치 공격, 잡기, 소환형 패턴처럼 서로 다른 행동을 상태 단위로 나누고, 공격이 실제로 닿는 순간에 충돌체와 효과가 실행되도록 연결했습니다. 특히 잡기 패턴은 손 뼈대 위치를 기준으로 대상을 붙이고 이후 피해 처리로 이어지게 했습니다.

  1. 01
    상태 전환

    패턴마다 준비·실행·종료의 흐름을 나누어, 다음 행동으로 넘어가는 조건을 명확히 했습니다.

  2. 02
    충돌과 위치 정보

    공격 위치와 범위는 충돌체로 다루고, 잡기처럼 캐릭터에 붙는 동작은 뼈대 행렬을 기준으로 처리했습니다.

  3. 03
    전투 피드백

    애니메이션·충돌·VFX의 실행 순서를 맞춰 보스 행동이 화면에서 자연스럽게 읽히도록 다듬었습니다.

03 / COLLABORATION

개별 기능을 끝내는 데서 멈추지 않고,
팀 코드의 연결 지점을 배웠습니다.

첫 DirectX 협업 프로젝트에서 VFX와 보스 로직은 다른 팀원의 캐릭터·네트워크·맵 구현과 맞물렸습니다. 기능을 독립적으로 만들기보다, 어떤 상태와 데이터가 상대 구현에 전달되는지 확인하며 접점을 조율하는 경험을 쌓았습니다.

배운 점. 전투 구현은 한 기능의 완성도로 끝나지 않습니다. 판정, 애니메이션, 효과, 다른 플레이어의 화면까지 같은 시간을 공유할 때 비로소 의도한 플레이 경험이 된다는 점을 확인했습니다.

04 / PROJECT CASE STUDY

Gunfire Reborn DX11

RENDERING FRAMEWORK & TOOL

게임 기능과 함께 다뤘습니다.

TYPE
Personal Project
PERIOD
2022.12.27 — 2023.02.14
ROLE
Rendering Framework & Tool
STACK
C++ · DirectX 11 · HLSL · Assimp · ImGui · FMOD

01 / LOADING & STATE

대기 시간을 분리하고,
상태 전환은 확장 가능한 규칙으로 바꿨습니다.

에셋과 프로토타입 생성은 로딩 스레드에서 처리하고, 메인 스레드와는 임계 영역으로 동기화했습니다. 캐릭터와 오브젝트의 행동은 단순 enum·switch 방식에서 Start·Tick·End를 갖는 상태 객체 흐름으로 확장했습니다.

LOADING THREAD

로딩과 플레이의 역할 분리

로딩 중 생성할 컴포넌트와 게임 오브젝트 프로토타입을 별도 흐름에서 준비하고, 완료 시점에 정리 작업까지 이어지도록 구성했습니다.

CUSTOM FSM

행동 전환을 함수로 관리

람다·템플릿·Builder 패턴을 활용해 상태의 시작·갱신·종료를 분리했습니다. 각 상태는 자신이 전환 가능한 다음 상태를 판단하도록 설계했습니다.

02 / MOVEMENT & NAVIGATION

움직임이 끊기지 않도록,
애니메이션 전환과 이동 경로를 함께 다뤘습니다.

상태가 바뀌어도 자세가 갑자기 튀지 않도록 뼈대 행렬을 보간했습니다. 맵 위 이동은 직접 생성한 폴리곤 셀을 기반으로 현재 위치를 찾고, 경계에서는 슬라이딩 벡터로 이동을 보정했습니다.

ANIMATION LERP
  1. 01
    Transform 보간

    스케일·위치는 선형 보간하고, 회전은 쿼터니언 slerp로 연결해 상태 전환의 이질감을 줄였습니다.

  2. 02
    전환 시간 제어

    상태가 바뀌는 순간이 아니라 정해진 보간 구간 안에서 포즈가 바뀌도록 해 이동과 공격의 연결을 다듬었습니다.

NAVMESH

약 1,800개 셀로 이동 범위 구성

삼각형·사각형 셀의 선분을 이용해 위치를 탐색하고, 경계를 넘으려는 이동은 벽을 따라 미끄러지는 벡터로 보정했습니다. 충돌체는 DirectXCollision의 Sphere·AABB·OBB를 용도에 맞춰 사용했습니다.

03 / RENDERING

보이는 범위와 빛의 처리 경로를 분리해,
장면 표현의 기준을 세웠습니다.

Assimp로 모델과 애니메이션 데이터를 불러오고, 카메라 바깥 모델은 Frustum Culling으로 제외했습니다. Deferred Shading과 Cascade Shadow Map, HLSL 기반 효과를 적용하며 장면이 그려지는 순서와 각 패스의 역할을 확인했습니다.

배운 점. 게임 기능이 늘어날수록 로딩, 상태, 데이터, 렌더링을 한 덩어리로 보지 않고 각자의 책임과 연결 시점을 명확히 해야 한다는 기준을 갖게 됐습니다.
